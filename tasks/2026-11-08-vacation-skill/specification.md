# Specification — 2026-11-08-vacation-skill

Продуктовая спецификация S2. Связка AI-ассистента мессенджера (локальная
LLM через Ollama) с графиком отпусков `график отпусков 2026.xlsx`
(5 листов по отделам, «грязные» форматы дат). Операторские решения
2026-11-08: гибридная роль LLM (детерминированный флоу + LLM-формулировка
ответа), только СВОИ даты, PR держится до живой проверки с ботом,
данные — гитигнорённый data-dir с ингестом в БД.

Контекст-мотивация: уже был живой инцидент, когда график отпусков,
загруженный как RAG-документ, «прилетал» ответом почти к любому вопросу
(комментарий в `backend/app/services/bot.py`). Поэтому график идёт
мимо RAG-пайплайна: отдельный детерминированный парсер, таблицы БД и
скилл-ветка до RAG-поиска. Загружать xlsx через `POST /documents/ingest`
запрещено (constraint).

## Пользовательские сценарии

### С1. Общий вопрос про отпуск → предложение → «да» → ответ (REQ-FLOW)

Юзер в AI-чате пишет «Хочу в отпуск, но не знаю, когда я могу».
Сообщение матчится ключевыми словами (морфология «отпуск/отпуска/
отпуске»), LLM не вызывается. Бот отвечает ровно: «Хотите узнать свои
даты по графику отпусков?» и запоминает состояние «ждём да/нет»
(TTL 10 минут, настройка). Дальше:

- **«да»** (словарь: да/давай/хочу/узнать/покажи/конечно/ага/ок/окей):
  - фамилия уже сохранена → сценарий С3 (сразу ответ);
  - фамилии нет → сценарий С2 (вопрос о фамилии).
- **«нет»** (нет/не хочу/не надо/позже/неа): бот выполняет ОБЫЧНЫЙ
  путь (RAG + LLM) с исходным вопросом юзера, состояние сбрасывается —
  юзер интересовался отпуском вообще, а не своими датами.
- **постороннее НЕ-отпускное сообщение**: состояние сбрасывается,
  сообщение идёт обычным путём как само по себе; **повторный
  отпускной вопрос** в ожидании — бот повторяет предложение с
  обновлённым исходным вопросом (юзер переформулировал тему, а не
  ушёл с неё); **cancel-слова** (отмена/стоп) — короткий ack и выход
  без сжигания попытки.

### С2. Запрос фамилии → валидация → сохранение (REQ-FLOW, REQ-STATE)

Бот спрашивает: «Подскажите вашу фамилию — найду вас в графике
отпусков». Свободный ввод:

- «отмена/стоп/отменить» → бот подтверждает выход из вопроса, ни
  одна попытка не сгорает (F-7);
- найден РОВНО один человек (токен-фамилия точна, ё/е и регистр
  нормализованы) → фамилия (каноническое ФИО из графика) сохраняется
  в БД навсегда (пока юзер сам не сменит) → сценарий С3;
- несколько кандидатов (например «Вишневский» без инициалов, если их
  два) → бот перечисляет кандидатов с инициалами и отделом, просит
  уточнить; попытки считаются;
- не найден → бот показывает похожие фамилии (difflib) и просит
  повторить; после 2 неудачных попыток — вежливый выход «не нашёл вас
  в графике, уточните у HR», состояние сбрасывается;
- повторный заход в другом чате/после рестарта: фамилия уже взята из
  БД, вопрос не задаётся (REQ-STATE: персистентность, раны stateless).

### С3. Немедленный ответ по графику (REQ-LOOKUP, REQ-LLMFMT)

Ответ собирается из БД: отсортированные периоды «ФИО с ДД.ММ.ГГГГ на
N день/дня/дней» (склонение: 1/21 день, 2–4 дня, 5–20 дней; в графике
есть «на 1 день»). Затем LLM (гибрид по решению оператора): в промпт
подкладываются ТОЛЬКО структурированные периоды (никаких RAG-чанков),
модель формулирует человекочитаемый ответ; при недоступности/ошибке
провайдера — готовый шаблон из тех же строк, бот никогда не молчит.

### С4. Явный вопрос про график → без предложения, сразу ответ (REQ-FLOW)

«Когда у меня отпуск по графику?» / «покажи график отпусков» — явная
фраза про график: предложение «Хотите узнать…» НЕ показывается, сразу
сценарий С3 (или С2, если фамилии ещё нет).

### С5. Чужой отпуск → только свои даты (REQ-PRIVACY)

«Когда отпуск у Иванова?» — бот не выполняет поиск по чужой фамилии:
отвечает, что даёт даты только по самому юзеру, и предлагает узнать
свои. Lookup по произвольной фамилии в свежем сообщении невозможен
технически: поиск идёт только по сохранённой фамилии юзера либо по
фамилии, которую юзер ввёл в ответ на прямой вопрос бота о СВОЕЙ
фамилии.

### С6. Обновление графика — постоянный механизм + инструкция (REQ-INGEST, REQ-RUNBOOK; D-13)

HR обновляет xlsx → оператор действует по инструкции
`docs/deployment/vacation-schedule.md`: кладёт файл в
`backend/data/` (гитигнор) и запускает ингест venv-интерпретатором
бэкенда стенда (шов D-11: `<backend-venv-python>
backend/scripts/ingest_vacations.py`, при необходимости
`--db <строка из операторского env>`; фактический путь интерпретатора
записан в самом ранбуке): старый снимок того же года
заменяется целиком, новый год ложится рядом, фамилии юзеров живут в
своей таблице и реингест не задевает (канонические ФИО). Если
человек исчез из нового снимка, бот при следующем вопросе видит
not_found по сохранённой фамилии, сам удаляет её, сообщает «график
обновился» и переспрашивает один раз (D-15). Реингест
идемпотентен, без правок compose. Авто-расписание (cron) — не цель:
механизм обновления = задокументированная команда оператора.

## Не-цели

- tool-calling у модели (нет поддержки в провайдере; фиксация на
  будущий контур);
- RAG-ингест графика (запрещён — прошлый инцидент);
- запрос чужих отпусков, админские отчёты, статистика по отделам;
- правки фронтенда (ответ скилла — обычное сообщение бота,
  `askBot` забирает его по `response_message_id`);
- редактирование/удаление сохранённой фамилии самим юзером
  (минимальный флоу; смена = повторный вопрос после «не нашёл»);
- нативный стриминг ответа скилла (Ollama-провайдер и так не стримит:
  `complete_stream` дегенеративен);
- автоматический реингест по расписанию (cron/наблюдатель папки) —
  механизм обновления ручной, по ранбуку.

## Приёмка и живой гейт

Автоматические критерии (AC-PARSE…AC-PROCESS) закрываются
детерминированными тестами с FakeBotProvider (шов
`app.state.bot_provider`, прецедент `test_bot_api.py`), живой Ollama
не нужен. AC-LIVE — живой диалоговый смоук на поднятом
compose+Ollama-стеке (отложен: бот сейчас недоступен): финальный аудит
без него BLOCKED, PR в dev не мержится до живой проверки (решение
оператора).
