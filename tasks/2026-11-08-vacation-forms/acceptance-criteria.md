# Acceptance criteria — 2026-11-08-vacation-forms

Каждый критерий привязан к требованию (plan.manifest.json `requirements`)
и к evidence-артефакту. Формат заявлений — specification.md; здесь
проверяемые утверждения.

## AC-TEMPLATES — санитизированные шаблоны и реестр

Три RTF-шаблона лежат в `backend/app/vacations/templates/` и получены из
операторских оригиналов заменой реквизитов и подчёркиваний на
плейсхолдеры (токены specification.md; кластер «\_\_.\_\_ 202\_\_ г.»
свёрнут в «{{start_date}} {{year}} г.», {{start_date}} = ДД.ММ;
«календарных дней» → {{days_word}} полной фразой — D-F-8/D-F-9/D-F-18).
Оригиналы — r7-office RTF: весь текст `\uNNNN*`-эскейпами, реквизиты
ищутся полностью-эскейпнутыми формами; группа `{\info}` (author несёт
третье реальное ФИО и вендора правовой БД) ВЫРЕЗАЕТСЯ ЦЕЛИКОМ —
структурный пин: в шаблонах нет `\info`. `forms/registry.py` декларирует
для каждой формы точный набор токенов, загрузчик читает файл, тест
сверяет: набор токенов шаблона == набор реестра; в байтах шаблонов нет
ни одного реального реквизита (коммитимые тесты проверяют вымышленные
аналоги; полный маркер-набор — только в локальном evidence
контроллера, D-F-10/D-F-16). RTF остаётся валидным: EV-3 открывает
каждый заполненный файл в Word.

## AC-RTF — детерминированный рендер

`forms/rtf.py`: escape — безопасный ASCII литералом, `\ { }`
экранируются, всё остальное (кириллица, «», — ) → `\uNNNN*`
десятичные эскейпы с `*`-фолбэком — профиль оригиналов,
интерпретация не зависит от кодовой страницы читателя (D-F-18, F-R1-1);
fill — байтовая замена токенов по словарю, заранее валидируется
соответствие ключей токенам шаблона (лишний/недостающий ключ —
ValueError с перечнем), после заполнения `{{` в байте не остаётся;
повторная генерация с теми же данными байт в байт воспроизводима.
Форматы значений из FormSpec: даты отпуска ДД.ММ (год — отдельный
{{year}}), дата заявления ДД.ММ.ГГГГ, {{days_word}} = полная фраза
«календарный день/календарных дня/календарных дней» (пины 1/2/14).
Всё — pytest.

## AC-INTENT2 — форм-интенты выше отпускных, увольнение и ложные срабатывания мимо

classify(): «оформи заявление на отпуск» → form_vacation;
«хочу перенести отпуск» / «заявление о переносе» → form_transfer;
«отпуск за свой счёт» / «без сохранения зарплаты» / «без содержания» →
form_unpaid; всё это — ДО schedule/vacation («заявление на отпуск»
содержит «отпуск» и не должно ловиться предложением дат). Ключевые
слова — точные словоформы по границам слов, БЕЗ стем/префикс-матчинга;
unpaid — только составные корроборированные фразы. Негативы:
«заявление на увольнение» → НЕ form-вид (D-F-15); «Как оформить
отпуск?» → vacation (родительский пин, не захватывается «оформи»);
голый «счёт»/«проверь счёт» → не form_unpaid; «нужен отпуск» без
заявление-ключей → vacation. Регресс родителя: «когда мой отпуск по
графику» → schedule, «хочу в отпуск» → vacation. pytest.

## AC-WIZARD — диалоговые сценарии трёх форм через бота

Интеграционные сценарии (app+client, FakeStorage, синтетический график):
(1) «оформи заявление на отпуск» с одним периодом → подтверждение →
«да» → файл-вложение с датами периода; (2) несколько периодов → выбор
«2» → файл с выбранным периодом; (3) своя дата «с 05.02.2026 на 10
дней» → распарсено → файл; (4) перенос: старый период из графика, новая
дата, дни по умолчанию = старым; (5) свой счёт: даты спрашиваются, дни
обязательны, морфология полной фразой «календарный день/дня/дней»
(пины 1/2/14); (6) «нет» на финальном подтверждении → отказ без файла;
(7) отмена в середине → чистое состояние, следующее обычное сообщение
идёт нормальным путём; (8) форм-сообщение во время awaiting_yes
родителя → визард стартует, состояние родителя чистится; форм-интент
ДРУГОГО вида в активном визарде → рестарт новым видом с чистым payload
(D-F-19); (9) нет фамилии → surname-шаг внутри визарда → найдено →
продолжение, каноническое имя сохранено; (10) битый ввод дат дважды →
вежливый выход; (11) TTL-истёкшее состояние ведёт себя как
отсутствующее; (12) «заявление на отпуск для Иванова» → только свой
канал, чужих данных не касается; (13) реквизиты не настроены → отказ со
ссылкой на ранбук, состояние не создаётся. Словарь шагов закрыт, юнит-пин
перебирает все объявленные `form:<kind>:<step>` и отказывает на > 32
символов (D-F-11).

## AC-DELIVER — вложение и отказы доставки

Файл: FakeStorage получает upload с content-type application/rtf и
именем «Заявление… — ФИО.rtf»; bytes содержат `\uNNNN*`-экранированные
значения; message.file_id проставлен; run succeeded;
run.attachment_file_id = file id; файл chat-scoped c owner = бот-юзер.
Отказы: files=None при исходе с вложением → run failed
'form_storage_unavailable'; исключение загрузки → run failed
'form_storage_failed' (retry-контур жив). Фронт не тронут (вложения уже
рендерятся).

## AC-RUNBOOK2 — операторский ранбук форм

## AC-REALFORMS — контроль реальных файлов (контроллер, локально)

Сгенерированные на РЕАЛЬНОМ графике и РЕАЛЬНЫХ реквизитах (env) три
формы для одного реального лица открываются в Word (COM), извлечённый
текст содержит ожидаемые ФИО/должность/даты/дни с корректной
морфологией полной фразы; в байтах шаблонов после санитизации нет
реальных реквизитов шапки и metadata-маркеров (контроль по локальному
маркер-набору evidence/privacy-markers.md — сами маркеры в репо не
входят). Артефакты — только в work/…/evidence/real-forms/.

## AC-LIVE2 — отложенный живой смоук (блокирует финал и PR)

НЕ исполняется воркером. Оператор на поднятом стеке (compose + Ollama,
после EV-4 родителя или вместе с ним): (а) полный визард «на отпуск» →
файл скачивается и открывается в Word с правильными датами/должностью;
(б) перенос с новыми датами; (в) свой счёт; (г) отмена в середине;
(д) повторная генерация после реингеста графика по ранбуку — без
рестарта кода; (е) незаданные реквизиты → отказ с подсказкой.
EV-4 (лог/скриншоты) кладётся в work/2026-11-08-vacation-forms/
evidence/live/. До квитка финальный аудит BLOCKED, PR не вливается
(зеркало D-3, D-F-0).
