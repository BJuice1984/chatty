# Decisions — 2026-11-08-mobile-messenger-ux

Журнал решений контроллера (кларификации оператора + замещения
блокеров по делегации «Для задач используй alk», 2026-11-08).

## D-1 — объём свайпов (кларификация оператора)

Вопрос: «подключены ли свайпы» сформулирован как вопрос. Оператор
выбрал «проверить и реализовать все три»: вьюер историй
(влево/вправо/вниз), возврат из чата, возврат из настроек. Исследование:
touch-обработки в src/ нет вообще — реализуем с нуля один классификатор.

## D-2 — каденция плашки автора (кларификация оператора)

«При смене автора»: подряд идущие сообщения одного автора плашку не
повторяют. Точная формула (уточнена ревью F-1): трекер хранит автора
предыдущего ЧУЖОГО несистемного сообщения; свои сообщения трекер не
обновляют — серия A, ME, A остаётся серией одного автора (без второй
плашки), а A, B, A даёт плашку на каждом чужом сообщении.

## D-3 — семантика свайпа из настроек

При открытой секции — закрыть секцию (та же ветка, что settings-back);
на корне /settings — Router.back(). Прямой go('/messenger') отвергнут:
ломает семантику истории (back-button уходил бы в противоположную
сторону), Router.back на глубокой ссылке просто ничего не делает —
приемлемая деградация.

## D-4 — идентификация бота: серверный is_bot

Эвристика display_name === 'AI' отвергнута: поле редактируемое,
магическая строка, коллизия с человеком. Решение: аддитивное поле
ChatMemberBrief.is_bot, вычисление в едином билдере to_member_brief
сравнением email с bot-конфигом (готовый идиом services/chats.py).
Ответ-only, без миграций. Отсюда второй воркстрим WS-BE-BOT и
зависимость FE от BE.

## D-5 — фикс мобильного переполнения историями

Корневая гипотеза: на <768 grid-колонка 1fr без minmax(0,…) + ширина
stories-списка в процентах → min-content вклад раздувает трек. Фикс —
зажим (minmax(0,1fr) + min-width: 0 на сайдбаре + width/max-width 100%
списка), безопасный для всех веток; обязательный живой смоук 390px до
и после. Десктоп/планшет не трогаем (там сайдбар фиксированной ширины).

## D-6 — кебаб-меню на переиспользовании

Modal + те же handleClick дескрипторов шапки; в дескрипторы добавляются
подписи menuLabel. Скрытие ряда — чистый CSS (<768), DOM общий для
обоих представлений (тестируемость jsdom без media queries).

## D-7 — стрелка настроек получает свой BEM-класс

chat__container-profile-arrow в profile-settings.hbs переиспользовал
чужой класс, чей блок удалён pack-2 (правильно — для строки профиля).
Ставим profile-settings-item__arrow + margin-left: auto (флекс-ряд):
семантика «у правого края контейнера» как до pack-2, без абсолютного
позиционирования.

## D-8 — AI-чип сообщений: свой класс, то же семейство

Визуал chat-list-user__ai-badge, но собственный messenger-класс — без
кросс-файловых селекторных сцепок; дублирование ~6 строк стилей
принято.

## D-9 — данные плашки автора

Срез chatUsers уже несёт login/email/avatar (контракт GET
/chats/{id}/members, own-адаптер мапит). Тултип — нативный title=email
(доступность бесплатно, отдельный компонент не заводим). Плашка не
рендерится, пока chatUsers не загружены (появятся на первом же
стор-эмите после загрузки).

## D-10 — автономный цикл и предавторизация (оператор, 2026-11-08)

Оператор: «проходи весь цикл в автономном режиме, блокеры решай сам,
но записывай, чтобы я смог прочитать. План авторизовываю заранее».
Контроллер замещает оператора на решении блокеров исполнения
(REWORK-циклы, уточнения в рамках frozen-скоупа); каждое замещение —
записью в этот журнал. Контрактные изменения (смена скоупа/write-set/
гейтов) остаются за оператором — при таком блокере прогон
останавливается с WAITING-записью. Авторизация исполнения получена
до freeze; старт — только после независимого ревью и lock. Шов с
orchestration.remediationMode="ask": ask-остановки (подтверждение
REWORK-циклов, локальные уточнения) контроллер исполняет сам по этой
делегации с журнальной записью; исключением остаются контрактные
изменения (скоуп/write-set/гейты) — по ним WAITING для оператора.

## D-11 — Windows-швы бэкенд-гейта (блокер базы, решён контроллером)

`npm run verify:backend` на этом стенде не резолвит `.sh` через cmd;
рабочий вызов — `PYTHON_BIN=<venv-интерпретатор бэкенда стенда> bash
backend/verify.sh` (локальный venv-путь с кириллическим именем юзера
нужно передавать 8.3-коротким именем; точный путь — в операторском
runbook и evidence-логе, из журнала путь нейтрализован — раунд 2
ревью F-R2-3). База dev @ dc65e03: pytest 339 passed, 4 failed —
все четыре `tests/unit/ingestion/test_converter.py` падают с WinError
193 (POSIX-only тесты: исполняют .sh через subprocess) — известная
специфика стенда по прецеденту 2026-10-25-chats-list-members
(progress_log: «одинаковы до и после, вне write-set»). Решение: гейт
WS-BE-BOT = полный прогон тем же вызовом; вердикт PASS при «все, кроме
ровно этих 4 известных падений, зелёные; новые тесты зелёные»; сами 4
не deselect'им — их вывод остаётся в evidence для сверки «до и после».
converter/rag вне write-set воркстрима (пишем только schemas/chat.py,
services/chats.py, два тест-файла), повлиять на них невозможно.

## D-13 — пост-freeze коррекции до адаптации (решено контроллером)

Две правки пакета ПОСЛЕ вердикта READY_TO_FREEZE, ДО workflow init,
обе без смены semantics:

1. **Схема манифеста**: canonical-валидатор adoption отклонил

   Правило D-11 перенесено внутрь строки второй команды

   идентична (D-10: не контрактное изменение).
2. **Mocha-база**: манифест фиксирует нижнюю границу 756 (число из
   журнала pack-2), фактическая база ветки — **766 passing**
   (rework-попытка pack-2 добавила тестов сверх 756 из заметки
   памяти). Контракт «выросло, 0 удалённых» строгое и выполняется
   относительно фактической базы 766; 756 остаётся валидной нижней
   границей. Evidence фиксирует счётчики 766 → выросло.

Обе правки видны в re-freeze коммите; reviewedPlanHash перевыпущен на
итоговый digest.
