# План: отпуска — мультигодичные графики, использованные дни и перенос остатка

Дата: 2026-11-24. Статус: план-документ на будущее (исполнение не начато).
Операторские решения зафиксированы (раздел 3). Когда решат запускаться —
этот документ входной материал для `agent-first-planning` (ALK-пакет,
ветка от `dev`, бэкенд-фича).

## 1. Проблема

Бот-ассистент отвечает по графику отпусков из одного — самого свежего по
году — снапшота. На практике нужно:

- видеть **несколько графиков сразу** (2026 и 2027 ингестнуты рядом), пока
  оба года актуальны;
- **автоматически забывать** прошедший год: с 01.01 бот не должен
  предлагать отпуск за закончившийся год — никакой привязки к конкретным
  годам в коде;
- учитывать **фактически использованные дни** (HR-выгрузка) и показывать
  остаток;
- **переносить остаток** на следующий год по правилу ТК РФ (ст. 124:
  неиспользованные дни используются в течение 12 месяцев после окончания
  года) и напоминать о сроке.

## 2. Как устроено сейчас (что переиспользуем)

Vacation-skill — детерминированная ветка бота до RAG:

```
сообщение → intent (app/vacations/intent.py)
  → фамилия: stored (vacation_names) или диалог (surname_flow.py)
  → VacationService.find()            # app/vacations/service.py
  → format_periods() → строки «ФИО с 21.12.2026 на 7 дней»
  → LLM перефразирует (prompts.py): «Отвечай ТОЛЬКО по строкам данных ниже»
```

Ключевые точки:

- `VacationService._latest_snapshot_rows()` (`service.py:67-79`) —
  единственное место выбора снапшота: `order_by(year desc).limit(1)`.
- Инвариант D-10 (`prompts.py`): в LLM уходят только структурированные
  строки, никогда RAG-чанки; LLM не «знает» график — он перефразирует.
  **Расчёты всегда в коде, не в LLM** — сохраняем.
- Инвариант D-2 (`skill.py`): поиск только по stored-имени или прямому
  ответу пользователя; произвольные фамилии из сообщений не ищем —
  сохраняем.
- Приватность (запрос оператора 2026-11-09): miss отвечает голым
  not_found, без подсказок похожих фамилий — сохраняем.
- Даты в `format_periods` уже с годом (`%d.%m.%Y`) — мультигодичные
  ответы не требуют нового формата строк.
- Инжест: `backend/scripts/ingest_vacations.py`, replace-семантика по
  (год, source_name), glob `график отпусков*.xlsx`; год в имени файла
  достраивает усечённые даты (`parser.py`). Runbook:
  `docs/deployment/vacation-schedule.md`.
- Модели: `vacation_schedules` (год, source_name, row_count),
  `vacation_periods` (FK CASCADE, full_name, department, position,
  start_date, days). Миграции: 015_vacations, 016_forms_segment — новая
  будет следующей по номеру.

## 3. Решения оператора (сняты 2026-11-23, не переспрашивать)

| Вопрос | Решение |
|---|---|
| Источник использованных дней | HR-файл (xlsx-выгрузка кадровой системы), инжест рядом с графиком |
| Правило переноса | ТК РФ ст. 124: остаток года N жив до 31.12.(N+1), потом сгорает; бот напоминает о сроке |
| Два графика в базе | Механизм без привязки к годам: окно релевантности от текущей даты (раздел 4.1) |

«Календарь на сервере» — это системные часы (`date.today()`; в коде уже
есть `datetime.now(UTC)`), докер-контейнеры наследуют часы хоста. Внешних
сервисов не нужно.

## 4. Архитектура

Ни одного захардкоженного года — вся семантика «относительно сегодня».

### 4.1 Релевантность снапшотов — окно от текущего года

`_latest_snapshot_rows()` → `_relevant_snapshot_rows(today)`:
снапшоты с `year >= today.year`. Матчинг фамилий — по объединению имён
релевантных снапшотов; периоды в ответе группируются по году.

- сегодня (для примера, 2026): релевантны 2026 и 2027 → оба в ответе;
- 01.01 следующего года: прошедший год сам выпадает из окна, его остаток
  становится переносом (4.2);
- инжест файла 2028 — просто третий снапшот в окне, кода не меняем.

Stale-семантика D-15 («stored-фамилия исчезла из графика») уточняется:
исчезла из ВСЕХ релевантных снапшотов → удалить имя и переспросить;
есть хотя бы в одном → отвечаем по имеющимся.

### 4.2 Перенос остатка — вычисляемый, не хранимый

Отдельная таблица переносов НЕ вводим: перенос выводим из данных по
правилу ст. 124. В момент запроса (для юзера с нормами по годам):

```
запас = [норма(today.year) − использовано(today.year)]          # текущий год
      + Σ по годам N < today.year:
            max(0, норма(N) − использовано(N))
            если today <= 31.12.(N+1)                            # живой перенос
```

Норма года = сумма `days` всех периодов человека в снапшоте года (уже в
БД). Использовано = сумма по usage-записям года (4.3). Материализация
понадобится только при появлении компенсаций/увольнений — тогда и
вернёмся.

### 4.3 Использованные дни — таблица + второй инжест

Новая модель `vacation_usages`: id, full_name, department?, start_date,
end_date?, days, source_name, (год выводим из start_date; либо храним
явно — решить при имплементации). Alembic-миграция — следующая по номеру
после 016.

CLI `ingest_vacation_usage.py` рядом с `ingest_vacations.py`: тот же
replace-паттерн по (год, source_name), тот же способ запуска на стенде
(docker cp в chatty-api-1, см. runbook vacation-schedule.md).
Продолжить тот же data-dir (`backend/data/`), отдельный glob (имя
утверждается по образцу файла, п. 7).

### 4.4 Строки в промпт

`format_periods` расширяется до «блока запаса» (пример для 2027 года):

```
График 2027: Иванов И.И. с 12.07.2027 на 14 дней; с 03.08.2027 на 14 дней
Использовано в 2027: 14 из 28 дней
Перенос с 2026: 7 дней — использовать до 31.12.2027 (ст. 124 ТК РФ)
```

SYSTEM_RULE в `prompts.py` дополняем: отвечать только по строкам,
переносимые дни не суммировать с планом молча — упоминать отдельной
строкой. Fallback без LLM — сырые строки (уже есть в `skill.py`).

### 4.5 Часы и тестируемость

В `VacationService` инжектируется `clock: Callable[[], date]`
(продакшн-дефолт `date.today`). Тесты «замораживают» дату и проверяют
переключение года — главный регрессионный сценарий фичи.

## 6. Тест-план (ключевые сценарии)

1. Два релевантных снапшота → ответ содержит оба года, сгруппирован.
2. Часы 31.12.N 23:59 → график года N ещё в ответе; часы 01.01.N+1 →
   графика N нет, появился перенос «с N» с дедлайном 31.12.N+1.
3. Часы 01.01.N+2 → перенос года N сгорел (не упоминается).
4. Использовано > 0 → «использовано X из Y»; использовано всю норму →
   только перенос (если есть).
5. Usage-факт вне графика (человек ходил не по плану) → остаток всё
   равно корректен (норма − использовано).
6. Stored-фамилия: исчезла из всех релевантных → D-15-поведение;
   есть в одном из двух → ответ по имеющимся.
7. Инварианты: D-10 (в LLM только строки), D-2 (поиск только по
   stored/ответу), приватность (not_found без подсказок).
8. Инжест-идемпотентность: повторный usage-инжест не дублирует.

- Минус-остаток (использовано больше нормы, «аванс») — клампить в 0 и
  отдавать предупреждение или отражать долг?
